3. AUTH SYSTEM: IMPLEMENTED
======================================================================

Endpoints
- POST /api/auth/otp/send
- POST /api/auth/otp/verify
- POST /api/auth/refresh
- POST /api/auth/logout
- GET /api/auth/me

Owning files
- backend/app/api/auth.py
- backend/app/services/auth_service.py
- backend/app/services/email_service.py
- backend/app/core/security.py
- backend/app/deps.py

How OTP send works
1. Client calls POST /api/auth/otp/send with an email address.
2. Email is normalized and rate limits are checked.
3. A 6-digit OTP is generated.
4. The OTP is bcrypt-hashed and stored in otp_requests.
5. Resend delivery is attempted.
6. The API returns request_id and expires_in.

How OTP verify works
1. Client calls POST /api/auth/otp/verify with request_id, email, and otp.
2. The API loads otp_requests by UUID.
3. It checks email ownership, expiry, consumed flag, and max attempts.
4. The hashed OTP is verified.
5. If the user does not exist yet, a users row is created.
6. access_token is issued.
7. refresh_token is issued into an HttpOnly cookie.
8. The OTP row is marked consumed.

Current provider notes
- Resend is the live delivery path.
- Verified sender domain: yaduraj.me
- If Resend credentials are absent, development mode logs the OTP instead of sending real email.

4. USER PROFILE + SELLER ONBOARDING: IMPLEMENTED
======================================================================

Endpoints
- PATCH /api/users/me
- POST /api/users/become-seller
- POST /api/users/seller/upi
- GET /api/users/seller/{user_id}/public

Owning files
- backend/app/api/users.py
- backend/app/services/user_service.py
- backend/app/schemas/user.py

PATCH /api/users/me
- Auth required
- Allows updating name and email
- Validates email format
- Rejects duplicate email addresses with EMAIL_TAKEN

POST /api/users/become-seller
- Auth required
- Creates seller_profiles row if missing
- Promotes user role to seller unless current role is admin
- Returns seller profile state
- Current created state is kyc_status=pending

POST /api/users/seller/upi
- Auth required
- Requires existing seller profile
- Validates UPI ID format
- Saves UPI ID as the seller payout identifier
- Marks upi_verified=false
- Moves kyc_status from pending to submitted
- Returns verification_status=FORMAT_VALID

GET /api/users/seller/{user_id}/public
- Public
- Returns safe seller summary only
- No private email or payout data is exposed

Important product note
- Aadhaar is not part of the primary frontend onboarding flow now.
- The live v1 seller flow is:
  - email OTP
  - full name
  - buyer or seller choice
  - become seller
  - save payout UPI
  - create first listing

- Seller must have saved payout UPI before creating a listing

6. FRONTEND FLOW THAT MATCHES BACKEND
======================================================================

Current intended app flow
1. User enters email
2. OTP is sent by backend via Resend
3. User verifies OTP
4. If name is missing, frontend asks for full name and buyer vs seller intent
5. Buyer continues to dashboard
6. Seller becomes seller, saves payout UPI, and continues into listings
7. Seller creates first draft listing

This is the product flow frontend should implement against today.
