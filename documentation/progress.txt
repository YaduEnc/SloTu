5. AUTH SYSTEM: IMPLEMENTED
======================================================================

Status
- Implemented
- Functional locally
- Tested

Endpoints
- POST /api/auth/otp/send
- POST /api/auth/otp/verify
- POST /api/auth/refresh
- POST /api/auth/logout
- GET /api/auth/me

Owning files
- backend/app/api/auth.py
- backend/app/services/auth_service.py
- backend/app/services/otp_service.py
- backend/app/core/security.py
- backend/app/deps.py

How OTP send works
1. Client calls POST /api/auth/otp/send with a phone number.
2. Phone number is normalized into +91XXXXXXXXXX format.
3. Rate limits are checked using otp_requests history.
4. A 6-digit OTP is generated.
5. The OTP is bcrypt-hashed and stored in otp_requests.
6. SMS dispatch is attempted through the OTP service.
7. The API returns request_id and expires_in.

How OTP verify works
1. Client calls POST /api/auth/otp/verify with request_id, phone, and otp.
2. The API loads otp_requests row by UUID.
3. It checks ownership, expiry, consumed flag, and max attempts.
4. The hashed OTP is verified.
5. If the user does not exist yet, a users row is created.
6. access_token is issued.
7. refresh_token is issued into an HttpOnly cookie.
8. The OTP row is marked consumed.

How refresh works
1. Client calls POST /api/auth/refresh with refresh cookie.
2. Refresh JWT is decoded.
3. Previous refresh JTI is blacklisted in Redis.
4. New access token is returned.
5. New refresh cookie is set.

How logout works
1. Client calls POST /api/auth/logout.
2. Refresh token JTI is blacklisted in Redis.
3. Refresh cookie is deleted.

How auth/me works
1. Client sends Authorization: Bearer <access_token>.
2. Shared dependency loads the authenticated user.
3. API returns user details plus seller_profile if available.

Important auth details already handled
- Indian phone normalization
- OTP hashing
- OTP attempt limits
- OTP send rate limits
- Refresh rotation
- Redis blacklist
- Invalid client host handling for INET rate-limit checks
- UUID-safe request validation
- Secure cookie configuration support via settings

Current local SMS behavior
- If Fast2SMS credentials are absent, development mode logs the OTP flow instead of sending a real SMS.
- Real provider failure returns SMS_PROVIDER_DOWN.

6. USER PROFILE + SELLER ONBOARDING: IMPLEMENTED
======================================================================

Status
- Implemented
- Functional locally
- Tested

Endpoints
- PATCH /api/users/me
- POST /api/users/become-seller
- POST /api/users/seller/upi
- POST /api/users/seller/aadhaar/send-otp
- POST /api/users/seller/aadhaar/verify-otp

Owning files
- backend/app/api/users.py
- backend/app/services/user_service.py
- backend/app/schemas/user.py

PATCH /api/users/me
Behavior
- Auth required
- Allows updating name and email
- Trims name input
- Validates email format
- Rejects duplicate email addresses with EMAIL_TAKEN

POST /api/users/become-seller
Behavior
- Auth required
- Creates seller_profiles row if missing
- Promotes user role to seller unless current role is admin
- Returns seller profile state
- Current created state is kyc_status=pending

POST /api/users/seller/upi
Behavior
- Auth required
- Requires existing seller profile
- Validates UPI ID format
- In development mode, marks UPI as verified immediately
- Stores upi_id and upi_verified on seller_profiles

POST /api/users/seller/aadhaar/send-otp
Behavior
- Auth required
- Requires existing seller profile
- Validates 12-digit Aadhaar format
- Creates a temporary KYC request in Redis
- Stores:
  - user_id
  - hashed KYC OTP
  - hashed Aadhaar last 4 digits
  - seller_profile_id
- Returns kyc_request_id

POST /api/users/seller/aadhaar/verify-otp
Behavior
- Auth required
- Loads the temporary Redis-backed KYC request
- Verifies ownership
- Verifies OTP
- Marks seller profile as:
  - aadhaar_verified=true
  - kyc_status=approved
- Stores only the one-way hash of Aadhaar last 4 digits
- Deletes temporary Redis request after success

Important note
- Aadhaar number itself is NOT stored in the database.
- Only the one-way hash of the last 4 digits is stored after successful verification.
