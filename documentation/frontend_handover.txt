2. BACKEND-READY USER FLOWS
======================================================================

Flow A: Email login
1. User enters email address
2. Frontend calls POST /api/auth/otp/send
3. User enters OTP
4. Frontend calls POST /api/auth/otp/verify
5. Backend returns access_token and user object
6. Backend also sets refresh cookie automatically
7. Frontend keeps access_token in memory

Flow B: First-login account setup
1. After OTP verify, inspect returned user
2. If user.name is missing, route to account setup
3. Ask for full name
4. Ask whether the user wants to continue as buyer or seller
5. Save the name with PATCH /api/users/me
6. If seller was chosen, call POST /api/users/become-seller
7. Seller users continue to /onboarding/upi
8. Buyer users continue to /dashboard

Flow C: Session restore
1. Frontend gets 401 on a protected call
2. Frontend calls POST /api/auth/refresh
3. If successful, backend returns a new access_token
4. Retry the original request once
5. If refresh fails, send user back to login

Flow D: Profile completion
1. Logged-in user opens profile page
2. Frontend calls GET /api/auth/me
3. User updates name/email
4. Frontend calls PATCH /api/users/me

Flow E: Become seller
1. Logged-in user clicks become seller
2. Frontend calls POST /api/users/become-seller
3. Backend creates seller_profile and role becomes seller
4. seller_profile comes back in response

Flow F: Seller UPI capture
1. User enters UPI ID
2. Frontend calls POST /api/users/seller/upi
3. Backend validates only the UPI format for now
4. Backend saves the UPI ID on seller_profile
5. UI should show this as saved / submitted, not bank-verified

Flow G: Seller listings
1. Seller opens /seller/listings
2. Frontend calls GET /api/listings/me
3. Seller can create a new listing from /seller/listings/new
4. Frontend loads GET /api/listings/services/catalog
5. Frontend submits POST /api/listings
6. Seller can pause/activate via PATCH /api/listings/{id}
7. Seller can remove via DELETE /api/listings/{id}

5. AUTH INTEGRATION RULES
======================================================================

Access token
- Returned by POST /api/auth/otp/verify
- Returned by POST /api/auth/refresh
- Send on protected requests as:
  - Authorization: Bearer <token>

Refresh token
- Stored by backend in HttpOnly cookie
- Frontend must not try to read it
- Browser sends it automatically to backend

Frontend storage recommendation
- Keep access token in memory
- If app reloads, call GET /api/auth/me or POST /api/auth/refresh to restore

Logout
- Call POST /api/auth/logout
- Then clear frontend in-memory auth state

401 behavior
- Try refresh once
- Retry original request once
- If still failing, send user to login

6. REQUEST / RESPONSE SHAPES FRONTEND MUST EXPECT
======================================================================

POST /api/auth/otp/send
Request
- { "email": "aman@example.com" }

Response
- { "request_id": "uuid", "expires_in": 300 }

POST /api/auth/otp/verify
Request
- { "request_id": "uuid", "email": "aman@example.com", "otp": "123456" }

Response
- {
    "access_token": "...",
    "token_type": "Bearer",
    "expires_in": 900,
    "user": { ... },
    "is_new_user": true|false
  }

POST /api/users/seller/upi
Request
- { "upi_id": "aman@okhdfcbank" }

Response
- {
    "upi_id": "aman@okhdfcbank",
    "upi_verified": false,
    "verification_status": "FORMAT_VALID"
  }

POST /api/listings
Request
- {
    "service_slug": "netflix-premium",
    "price_paise": 17900,
    "duration_days": 30,
    "slots_total": 2,
    "description": "Family plan, India region"
  }

Response
- listing object in status=draft

GET /api/listings/services/catalog
Response
- array of supported services:
  - slug
  - name
  - category
  - logo_url
  - tos_sharing_allowed

7. ERROR HANDLING CONTRACT
======================================================================

All errors use
- { "error": { "code": "STRING_CODE", "message": "Human readable", "details": {} } }

Important error codes frontend should handle explicitly

Auth
- INVALID_EMAIL
- RATE_LIMITED
- OTP_INVALID
- OTP_EXPIRED
- OTP_TOO_MANY_ATTEMPTS
- UNAUTHORIZED

Profile
- EMAIL_TAKEN

Seller onboarding
- SELLER_PROFILE_REQUIRED
- INVALID_UPI_ID
- SELLER_ONBOARDING_INCOMPLETE

Listings
- INVALID_SERVICE
- INVALID_LISTING_STATUS
- LISTING_SLOT_CONFLICT
- ACTIVE_ORDERS_EXIST
- LISTING_NOT_FOUND

9. PRODUCT / UX GUIDANCE
======================================================================

What frontend should call the current seller verification
- UPI submitted
- Payout UPI saved
- Verification pending

What frontend should NOT claim right now
- UPI verified
- bank verified
- payout account verified
- government ID verified
- full legal KYC completed

Good seller UX copy
- "Add your payout UPI ID"
- "We currently validate the format and save your payout handle"
- "Full bank-side verification can be added later without changing your listing flow"
