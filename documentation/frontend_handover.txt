2. BACKEND-READY USER FLOWS
======================================================================

These flows are ready for frontend integration now.

Flow A: Phone login
1. User enters mobile number
2. Frontend calls POST /api/auth/otp/send
3. User enters OTP
4. Frontend calls POST /api/auth/otp/verify
5. Backend returns access_token and user object
6. Backend also sets refresh cookie automatically
7. Frontend stores access_token in memory, not localStorage if possible

Flow B: Session restore
1. Frontend gets 401 on a protected call
2. Frontend calls POST /api/auth/refresh
3. If successful, backend returns a new access_token
4. Retry original request
5. If refresh fails, send user back to login

Flow C: Profile completion
1. Logged-in user opens profile page
2. Frontend calls GET /api/auth/me
3. User updates name/email
4. Frontend calls PATCH /api/users/me

Flow D: Become seller
1. Logged-in user clicks become seller
2. Frontend calls POST /api/users/become-seller
3. Backend creates seller profile and role becomes seller
4. seller_profile comes back in response

Flow E: Seller UPI capture
2. User enters UPI ID
3. Frontend calls POST /api/users/seller/upi
4. Backend checks only the UPI format for now
5. Backend saves the UPI ID on the seller profile
6. UI should show this as saved / submitted, not verified

Flow F: Optional Aadhaar path
1. User enters Aadhaar number
2. Frontend calls POST /api/users/seller/aadhaar/send-otp
3. User enters Aadhaar OTP
4. Frontend calls POST /api/users/seller/aadhaar/verify-otp
5. This is optional in current v1 direction

5. AUTH INTEGRATION RULES
======================================================================

Access token
- Returned by POST /api/auth/otp/verify
- Returned by POST /api/auth/refresh
- Send on protected requests as:
  - Authorization: Bearer <token>

Refresh token
- Stored by backend in HttpOnly cookie
- Frontend must not try to read it
- Browser sends it automatically to backend

Frontend storage recommendation
- Keep access token in memory
- If app reloads, call GET /api/auth/me or POST /api/auth/refresh to restore

Logout
- Call POST /api/auth/logout
- Then clear frontend in-memory auth state

401 behavior
- Try refresh once
- Retry original request once
- If still failing, send user to login

6. REQUEST / RESPONSE SHAPES FRONTEND MUST EXPECT
======================================================================

POST /api/auth/otp/send
Request
- { "phone": "+919876543210" } or plain Indian 10-digit number, backend normalizes

Response
- { "request_id": "uuid", "expires_in": 300 }

POST /api/auth/otp/verify
Request
- { "request_id": "uuid", "phone": "9876543210", "otp": "123456" }

Response
- {
    "access_token": "...",
    "token_type": "Bearer",
    "expires_in": 900,
    "user": { ... },
    "is_new_user": true|false
  }

GET /api/auth/me
Response
- user object
- includes seller_profile when user is seller / has one

PATCH /api/users/me
Request
- { "name": "Aman Kumar", "email": "aman@example.com" }

Response
- updated user object

POST /api/users/become-seller
Response
- { "seller_profile": { ... } }

POST /api/users/seller/upi
Request
- { "upi_id": "aman@okhdfcbank" }

Response
- {
    "upi_id": "aman@okhdfcbank",
    "upi_verified": false,
    "verification_status": "FORMAT_VALID"
  }

POST /api/users/seller/aadhaar/send-otp
Response
- { "kyc_request_id": "uuid" }

POST /api/users/seller/aadhaar/verify-otp
Response
- seller_profile object

7. ERROR HANDLING CONTRACT
======================================================================

All errors use
- { "error": { "code": "STRING_CODE", "message": "Human readable", "details": {} } }

Important error codes frontend should handle explicitly

Auth
- INVALID_PHONE
- RATE_LIMITED
- OTP_INVALID
- OTP_EXPIRED
- OTP_TOO_MANY_ATTEMPTS
- UNAUTHENTICATED

Profile
- EMAIL_TAKEN

Seller onboarding
- SELLER_PROFILE_REQUIRED
- INVALID_UPI_ID
- KYC_OTP_EXPIRED
- KYC_OTP_INVALID
- KYC_REQUEST_FORBIDDEN

Validation
- INVALID_REQUEST

Frontend behavior recommendation
- map `code` to user-friendly UI messages
- keep raw `message` for fallback display
